# 前后端开发标准（执行版）

## 1. 设计原则
- 模块化优先：按业务域拆分，避免“巨型 service/store 文件”继续膨胀。
- 正确性优先：先保证一致性与可回放，再做局部性能优化。
- 可维护优先：统一命名、统一错误语义、统一变更流程。

## 2. 后端（Go）分层标准
### 2.1 分层职责
- `httpapi/`：协议适配、参数校验、鉴权、错误映射。
- `game/`：业务编排与流程控制，不直接写 SQL。
- `store/`：唯一数据访问入口，负责事务、锁、幂等落库。
- `scheduler/`、`market/`、`ws/`：跨域能力模块，禁止反向依赖上层协议。

### 2.2 事务与并发
- 交易、队列结算、任务提交、装备成长必须单事务。
- 热点行读写需显式锁策略（例如 `FOR UPDATE`）并控制锁粒度。
- 失败必须显式返回结构化错误，禁止吞错和静默回退。

### 2.3 幂等与重试
- 外部可重试命令必须提供 `idempotency_key`。
- 幂等记录落库并受唯一约束保护。
- 重试仅允许在幂等边界内进行，不能重复扣减资源。

## 3. 前端（Vue）分层标准
### 3.1 职责划分
- `views/`：路由页面编排，不放重业务逻辑。
- `stores/`：状态聚合与衍生计算。
- `services/`：HTTP/WS 协议访问与错误码映射。
- `components/`：可复用、单职责 UI 组件。

### 3.2 状态更新策略
- 优先事件驱动（WS patch + 本地归并），减少固定轮询。
- 关键状态（玩家资源、队列、仓库）采用单一 store 真值源。
- 错误统一按 `error.code` 分流并 i18n 映射。

## 4. 协议与错误码标准
- HTTP 响应统一：`ok/data/error/ts`。
- WS 响应统一：`type/ok/data/error/ts`。
- 错误码由后端定义、前端集中映射，禁止页面散落硬编码文案。
- 协议选型强制规则：
  - 需要可重试/幂等/审计回放的请求，必须使用 HTTP（例如配置保存、交易、仓库写操作）。
  - 需要低延迟交互并伴随服务端持续推送的链路，使用 WS（例如动作队列控制、实时状态 patch）。
  - 同一“写”语义仅允许一个协议入口，禁止同一写操作同时提供 HTTP 和 WS 两条实现路径。
  - 读路径采用“HTTP 快照 + WS 增量”组合：初始加载走 HTTP，后续变化走 WS 推送。

## 5. 配置与数据标准
- 游戏配置唯一来源：`packages/game-data/source/*`。
- 前后端禁止维护双份业务常量。
- 配置变更流程：先改 source -> 生成产物 -> 改服务逻辑 -> 改前端展示。

## 6. 数据库设计标准
- 命名统一：`snake_case`。
- 主键统一：`id BIGSERIAL`（或业务表的等价 bigint 主键策略）。
- 审计字段统一：`created_at`、`updated_at`。
- 业务约束必须数据库落地（`NOT NULL`、`CHECK`、`UNIQUE`、`FK`）。

## 7. 可观测与回滚
- 核心链路必须有结构化日志：交易、队列推进、任务结算、装备操作。
- 迁移发布必须具备回滚方案与数据校验脚本。
- 任何破坏性改动只允许在明确“可清库”阶段执行。

## 8. 中间件职责边界（PG / Redis / NATS）
- PostgreSQL：交易与库存真值源，承载事务一致性、幂等记录、审计数据。
- Redis：共享瞬时状态与高频控制面（请求限流计数、窗口 TTL、热点缓存）。
- NATS：跨实例事件广播与异步解耦（WS 扇出、领域事件传播）。
- 禁止把“需要审计回放”的核心写模型仅放在 Redis/NATS。

## 9. 限流方案标准（固定窗口）
- API 限流统一采用 Redis 固定窗口计数（多实例共享），窗口参数来自 `global-config`。
- Redis 不可用时允许降级到进程内限流，但必须记录日志并保持 `Retry-After` 语义。
- 当前重置策略：运维按 key 范围手工删除（不暴露业务管理接口）。

## 10. 质量门禁
- PR 必须通过 `harness`（game-data、server、web build/unit/e2e）。
- 若迁移变更触发表结构变化，必须同步更新 `docs/backend/database-schema.md`。
