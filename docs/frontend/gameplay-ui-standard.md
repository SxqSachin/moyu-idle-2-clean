# Gameplay UI Standard（AI执行版）

## 目标
- 统一游戏内玩法页面（首页、动作菜单、仓库、属性强化链路）的信息层级与交互节奏。
- 参考 `deep-article` 的玩法组件组织方式，但保持本项目技术栈与规范：Vue3 + Element Plus + Tailwind + i18n key 驱动。
- 移动端优先（强制）
- 迁移主规范参考：`docs/frontend/deep-article-ui-migration-spec.md`（菜单顺序、动态菜单驱动、tab-query 联动）。

## deep-article 对齐约束（新增）
- 菜单迁移必须按 deep-article 顺序执行，不允许按“现有路由便利性”跳序改造。
- 必须先完成菜单驱动层（registry + dynamic resolver），再迁移各菜单面板。
- 动态菜单（动作主类）必须由配置驱动生成，不允许手工散落菜单项。
- 非路由型新菜单在后端未就绪前，必须使用完整占位面板：
  - 保留完整信息布局；
  - 提交按钮禁用；
  - 显式文案“后端待接入”。

## 统一页面骨架
- 顶层结构固定为：`GameShell(菜单/状态栏) -> 页面Header -> 内容卡片区`。
- 页面Header必须包含：
  1. 页面标题（i18n key）
  2. 一行辅助说明（该页面核心收益或风险）
  3. 至少一个刷新或同步动作（显式更新入口）

## 动作类页面（训练/劳作/探索/制作/战斗）模板
- 每个动作卡必须包含四段信息：
  1. **消耗**（金币/道具/体力）
  2. **收益**（道具/属性经验）
  3. **执行参数**（次数、队列模式）
  4. **状态**（当前排队/运行/可执行）
- 队列卡必须固定展示：
  - 剩余总时间
  - 已完成/总次数
  - 预计完成时间（ETA）
  - 当前状态徽标（pending/running/done/failed）
- 展示边界：执行队列仅允许在首页展示；非首页动作页不得展示执行队列面板。

### 战斗配置页（战斗子规范）
- 规则配置必须使用可视化编辑器（组内 AND / 组间 OR），禁止要求玩家手填 JSON。
- 技能槽位必须支持拖拽调整优先级，槽位顺序即释放顺序。
- 可配置技能列表必须来自“玩家已拥有技能”，不允许展示未拥有技能。
- 战斗配置页需提供“已拥有技能”增删入口，前端通过后端 API 维护 `player_owned_skills`，避免手工改库。
- 空槽位必须可保留并显式展示“未配置技能”；战斗判定应跳过空槽继续检查后续槽位。
- 进入战斗配置页时若发现失效技能（不再拥有），必须一次性弹窗确认并清空对应槽位。
- 战斗过程面板的单位布局应按阵营+站位呈现（左侧后→中→前，右侧前→中→后），不使用纯文本堆叠表达站位。
- 战斗连线必须具备方向语义（箭头或飞行动画轨迹），可直观看出行动发起者与目标。
- 战斗单位卡片需抽象为独立组件；悬浮详情至少包含：`attributes(key+value)`、`skillIds` 映射技能列表（含 `skillCooldowns`）、`equipmentInstanceIds`、`buffs(buffId/剩余时长/payload)`。
- 回放展示以服务端快照 + 事件增量驱动，不依赖页面轮询；HP/MP/存活状态必须与回放推进同步。
- 仅首场读取玩家实时属性，后续场次沿用战斗内继承状态；UI 不应在场间强行刷新为外部实时属性。

## 仓库列表模板
- 每个物品卡必须直接可读：
  - 物品名（短名）
  - 数量（最少显示 `xN`）
  - 实例标识（`#instanceId`）
- 每个物品块必须有 tooltip 或详情面板：
  - 完整名称
  - 强化等级
  - 描述/用途（若可得）
- 只显示实例 ID 不显示物品信息是禁止项。

## 强化/附魔/异变信息展示模板
- 在操作按钮附近固定展示材料视图：
  - 需求数量
  - 当前持有数量
  - 是否可负担（布尔状态）
- 强化需额外展示：
  - 金币消耗 + 持有金币
  - 保护材料（若存在）
  - 成功率/失败降级规则
- 附魔需展示可选书籍列表与持有量，不允许盲操作。

## 交互一致性
- 所有成功/失败反馈用 `ElMessage`，并走统一错误码映射。
- 可重试动作必须在失败提示后保持可重试状态，不可静默失败。
- 所有异步按钮在请求中需要体现加载或禁用态。
- 关键交互必须支持触控完成，不得依赖 hover 才可达成关键操作。
- 仓库相关交互需复用统一组件，保证物品渲染与错误反馈语义一致。

## 组件单一职责（强制）
- 仓库列表与物品详情能力必须拆分为可复用组件，禁止页面内重复实现同类渲染逻辑。
- 页面容器只负责数据编排与 API 调用；列表组件只负责展示与交互事件抛出；工具函数与类型定义独立维护。
- 可复用组件必须支持：
  1. i18n 文案输入（而非内部硬编码）；
  2. Web + Electron 双端一致行为；
  3. 在不同页面按需组合（如仓库页、首页快捷区）。

## i18n 与数据来源
- 页面可见文字必须来自 i18n key，不可直接硬编码中文或英文。
- 物品信息、动作成本、奖励配置统一来源：
  - `packages/game-data`（后端加载）
  - 前端通过 API 获取，不维护重复常量表

## Web + Electron 兼容要求
- 禁止使用仅浏览器环境可用但无降级的 API（例如未经保护的 Notification、Clipboard 高权限调用）。
- 页面布局使用响应式断点，不依赖 hover 才能完成关键操作。

## AI执行检查清单（提交前）
1. 页面主标题、按钮、空态文案是否全部走 i18n key。
2. 动作卡是否完整展示消耗/收益/执行参数/状态四段。
3. 仓库列表是否可直接读出“是什么 + 有多少”。
4. 强化/附魔/异变是否展示材料需求与持有差。
5. 错误码是否可被 `resolveErrorMessage` 映射到用户可读文案。
6. 菜单是否满足 deep-article 顺序与分组（含动态动作菜单插入位）。
7. 菜单选择、刷新与分享链接是否保持 `tab` 查询参数一致性。
8. 后端未就绪面板是否保持“完整界面 + 禁用提交 + 待接入标识”。
9. 迁移模块是否在同次提交补齐 `zh-CN/zh-TW/en-US/ja/ko/ru` 文案。

## 禁止项
- 禁止在玩法页面新增硬编码业务文案。
- 禁止在仓库中只显示 `#instanceId` 而不显示物品标识。
- 禁止把 `packages/game-data` 已有信息复制一份到前端常量手工维护。
- 禁止在首页以外的页面展示执行队列。
- 禁止提交非移动端优先（桌面优先）的新页面布局。
