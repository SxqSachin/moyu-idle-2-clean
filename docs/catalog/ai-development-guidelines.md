# AI 开发规范（前后端）

## 1. 总则
- 代码优先目标：**可读性 > 可维护性 > 可扩展性 > 性能优化细节**（在满足性能基线前提下）。
- 任何功能必须具备：输入/输出定义、状态流转、失败处理、幂等策略。
- 禁止“静默失败”：错误必须结构化返回或日志可追踪。

## 2. 后端（Go）组织规范
- 按业务域拆分文件，避免巨型文件：
  - `httpapi/`：按协议拆分（`http_*.go`、`ws_*.go`、`ws_actions.go`）。
  - `store/`：按领域拆分（`market_*.go`、`action_queue.go`、`inventory_*.go`）。
  - `game/`：只保留调度编排，不承载 SQL 细节。
- 事务规范：
  - 读写一致性链路（扣成本/发奖励/状态推进）必须单事务。
  - 并发热点行必须显式锁（`FOR UPDATE`）并说明锁粒度。
- 协议规范：
  - 查询走 HTTP，变更命令走 WS command。
  - 每个 WS command 需要 `requestId/idempotencyKey` 语义。
  - 推送事件只发增量，不发冗余全量大包。
- 库存收口规范：
  - 任何库存增减必须走统一入口（`AddInventoryItemTx` / `RemoveInventoryItemTx`），禁止业务模块直接改 `player_items`。

## 3. 前端（Vue）组织规范
- 页面只做编排，业务逻辑下沉到：
  - `stores/`：状态聚合
  - `services/`：协议访问
  - `components/`：可复用 UI（如 `ActionPanel`、`ItemCard`）
- 组件职责单一：一个组件只处理一个主用例，不混杂多个业务域。
- 状态更新优先事件驱动，不依赖固定轮询。

## 4. 配置与数值规范（game-data）
- 单一数据源：所有可调参数必须在 `packages/game-data/source/`。
- 支持策划 Excel 工作流：`source/game-data.xlsx`（sheet 名=表名）。
- 配置字段必须显式类型化（数值/JSON），禁止隐式字符串拼接语义。

## 5. 性能与扩展规范
- 放置队列：在线推送 + 离线快进，禁止全量轮询。
- 大规模战斗：使用离散事件调度（DES），按 `battle_id` 分片处理。
- 缓存策略必须带版本失效（写后失效 or 版本递增），避免脏读。

## 6. 可读性规范
- 命名要求语义化，避免缩写堆叠。
- 单函数建议控制在“单一职责可读范围”；超过则拆分。
- 注释只解释“为什么”，不复述“做了什么”。

## 7. AI 变更流程要求
1. 先改配置/协议定义，再改后端，再改前端，最后补文档。
2. 每次提交至少包含一条“关键链路可运行”的闭环。
3. 先保证正确，再做性能优化；优化需有可观测指标支撑。

## 8. 上下文一致性与需求落地标准（新增）
- 每次开发前先固定 5 个输入：**目标场景、约束条件、输入输出契约、错误码语义、验收口径**。
- 对“首页/仓库/队列/探索”等高频术语建立统一词典，避免同义词漂移造成实现偏差。
- 跨回合必须复用同一数据源：配置只认 `packages/game-data`，协议只认 `ok/data/error/ts`。
- 任何用户明确决策（如破坏性清理策略）必须立即写入计划与文档，后续实现不得自行偏离。

## 9. AI 执行检查清单（新增）
1. 变更前：列出受影响模块与依赖文档，并标注“为什么改”。
2. 变更中：每个接口/事件改动都同步更新调用方和文档，不留隐式行为。
3. 变更后：确认无旧流程残留；若采用破坏性策略，必须附清理脚本和执行说明。
4. 复盘项：记录一次失败原因与防复发规则，沉淀到本手册。

## 10. 破坏性操作默认策略（新增）
- 开发阶段默认允许破坏性变更，不要求兼容层与迁移层。
- 触及历史脏数据时，优先“直接清理 + 脚本化执行”，避免长期双轨逻辑。
- 所有破坏性清理都必须给出可重复执行脚本与回显检查 SQL。
