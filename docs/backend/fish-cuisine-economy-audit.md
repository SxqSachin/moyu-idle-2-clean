# 鱼料理数值与经济审视

日期：2026-09-05。当前共 30 道鱼料理、16 个系列；本页保留原有 22 道的审视，新增 8 道见 [初产业与转换料理](primary-work-cuisine-balance.md)。只为采集、挖矿、畜牧开放受限主产物加成，不开放通用制作增产与返料。

数据依据：`source/json` 中当前物品的 `useOperationEffectId`，不是同名前缀的历史效果定义。历史成品继续保留自己的冻结数值，不能用下表倒推旧成品。

## 结论

这套料理有明确用途，但并不是每一道都适合日常吃、也不是每一道都保证经济回本。当前最值得观察的是：

1. 一次型强化 / 灌注烤鱼与十分钟鱼汤的连续操作性价比差距。两者单次强度接近，不代表整份价值接近。
2. 普通钓鱼用两尾鱼换有限次概率加成，未必能回本；价值应来自挑战更贵的鱼和跨过断线阈值，而非无脑循环喂自己。
3. 月璃双珍确实是微调概率的高级消耗品，适合剩余高级鱼的长期消耗，不适合作为普通玩家必备材料。
4. 快手只提高处理速度，不提高单件回报。但已有商店 / 转换经济循环仍需用生产价格单独审计，不能把“没有新增金币”当作完全无风险。

本轮不擅自把全部旧料理改成更强的数值。先明确适用场景、保留原单次上限；点金增金覆盖当前允许点金的物品，不再限制首领战利品。下面的待观察项是平衡风险，不是已经证明的漏洞。

## 数值口径

- 标准：自动选鱼制作，只用默认数值。
- 顶配：两尾鱼的长度分位、同长度体重分位均达到 1；特质均值为 1。是理论组合边界，不代表任意大鱼都能达到。
- 三变异：整份料理去重后，闪光 1.50 × 棱彩 1.10 × 彩虹 1.10 = 1.815。同种变异不会因两尾鱼都有而重复计算。
- 长度按鱼种归一化；重量按该长度的体况归一化，避免同一份长度成长又被重量计算一次。
- 下表中的百分比为效果参数；最终成功率仍受各玩法原有保底、封顶约束。

每次实际开工匹配并消费一次，而不是成功才消费；失败仍用掉次数。次数不随离线流逝，鱼汤按现实时间过期。开工时已有的效果会冻结，结算时过期不取消，后来吃的料理不追补正在执行的操作。

烤鱼的质量乘数只在明确配置 `lifetimeScaling.charges` 的快手、聚金配方中增加次数。其他烤鱼按各自棱彩奖励增加次数；不能把所有烤鱼都乘 1.815。月璃始终一份一次。

容量按每种材料当前无料理上限计算，固定额外数量与比例额度取高，不是相加；还受原容量两倍的额外额度限制、材料单位对齐和库存限制。不是直接给成品全部属性加同等百分比。

三种传说材料同次灌注时，霜月对三种分别增加额度，但整次仅消耗一个次数，成功率代价不因材料种类重复三遍。若同时使用不同档容量料理，匹配的不同料理代价会合并，应看操作控件的最终成功率。

奶香仅覆盖普通材料灌注（含组合），不覆盖独立的鱼类灌注。其 +5% / 最高 +10% 能抵消一部分容量代价，但需要额外一份料理，不构成免费取消风险。

## 新料理成本与价值

全部烤鱼需要煤炭 2，鱼汤需要晨露 3。下列经济基准合计只用于比较资源量级，不是 NPC 售价或玩家市场价；均未计鱼的机会成本。

| 料理 | 两种鱼，各 1 尾 | 其他配料（另加煤炭或晨露） | 其他配料含燃料经济基准 | 基础制作耗时 |
| --- | --- | --- | ---: | ---: |
| 蜜焰快手烤鱼 | 欧鲢、雅罗鱼，普通 | 甜花蜜 3、苔光孢子 1 | 122 | 50 秒 |
| 曦蜜聚金烤鱼 | 鲤鱼、欧洲鲃，罕见 | 曦光花蜜 3、牛奶 2、苔光孢子 1 | 255 | 65 秒 |
| 曦蜜聚金鱼汤 | 同上 | 同上 | 241 | 75 秒 |
| 月璃双珍烤鱼 | 莲纹锦鲤、璃背箭鱼，史诗 | 月露 4、瓶装星光 1 | 442 | 90 秒 |

霜月仍用高级鱼和月露 24、瓶装星光 12；仅烤鱼的非鱼资源基准为 3782，显著高于新聚金料理。它购买的是稀缺灌注材料的容量突破，不应拿额外产币料理的直接回本速度衡量。

### 什么时候值得吃

- **容量、精度**：做终局 / 关键装备时有意义；随便做低价过渡物品可能不值得。容量不会降低材料成本，多放材料本身就是更高投入。三档容量隔离，不会从低档反复叠到神话。
- **奶香**：以常见、罕见鱼支持昂贵材料灌注，价值容易理解。若原成功率已经接近上限，实际收益会变小，应以控件增量而非料理文字判断。
- **凝神**：适合单次失败代价高的强化，不适合用来浪费在高成功率低等级装备上。
- **稳线**：跨过断线压力阈值时价值明显；本来就不会断线时意义很小。
- **收竿、芦岸**：更适合较高价值目标。标准芦岸烤鱼的 12 杆 × 10% 最多相当于 1.2 次额外上钩机会，还没算断线、收鱼失败和概率封顶。因此不能宣称消耗两尾鱼后钓普通鱼必定回本。
- **快手**：正常单次 8～22.8 秒时，标准 20 次节省约 140～436 秒；若玩家已经把正常耗时压到 2 秒，标准仅节省 20 秒，可能抵不过制作时间与食材。定位是提前备餐、集中清库存，不是高效率角色必吃。
- **聚金**：全部合法点金输入均生效，包括普通材料、制作产物和商店可购买物品；不应该为了吃料理而点掉本来要灌注、制作的珍贵素材。例如基准 40000 的狼王獠牙，标准料理单次成功额外 1200～1520 金币，顶配 3000～3800。失败不给钱；这些不是期望收益。低价物品的额外金币可能因逐件取整为 0，因此应集中用于高价值闲置材料，而非把它视为必吃料理。
- **月璃**：60/28/8/4 的原始池，传说从 4% 变成标准 4.35%、顶配 4.85%；史诗从 8% 变成 8.70%、9.71%。是长期小幅偏移，不是保底。两个史诗鱼换这点增益，普通阶段可能显得昂贵；因此不再额外要求月华精粹，保留为高端余粮消耗，观察使用率再调成本，不直接抬高传说概率。

### 烤鱼与鱼汤是否互相淘汰

同系列互斥，不把次数与时间强度叠加。同组加速点金、增金点金也互斥。

鱼汤在有库存、连续操作、多助手并发时明显占优；烤鱼的优势是不怕过期、零散操作更稳。一次型烤鱼在短耗时连续灌注中尤其弱，仅靠单次强 10%～20% 很难抵消鱼汤能覆盖多次的差距。

暂不擅自改掉此前确认的一次 / 十分钟规则。建议上线后按“每份实际受益操作数、使用后零受益比例、两类制作占比”检查；若单次烤鱼长期几乎无人制作，再选择提高其份量，或让同系列鱼汤增加配料成本，不继续拉大单次效果强度。

## 套利审视

### 已落实的防线

- 增金范围与原点金物品准入一致，不再维护首领白名单或商店来源否决。资格预览和实际开工共用服务端点金准入函数，仍排除货币、装备、任务道具等原本不可点金的物品；不改变原有等级、库存等开工校验。
- 每件成功输入独立计算 `floor(幸运倍率前金币 × 料理比例)`；不再乘幸运、不返还输入、不生成第二次点金。整数边界检查阻止额外金币相加溢出。
- 增金与一秒点金互斥，避免时间型增金因一秒点金扩大覆盖数。它限制速度，不替代材料来源审计。
- 不开放普通动作双产物 / 模板返料。烹饪不会凭空返还高级鱼或复制带数值成品。
- 附魔只调整已有合法稀有度的权重；候选没有高稀有度，或只剩高稀有度导致比例不变，不消费料理。不会新增神话候选或改写静态规则。
- 当前附魔池不包含已设置单装备次数上限的词条；未来扩展此类候选时，必须先处理“随机后超限回滚”的拒绝采样风险，不能当作天然安全。

### 不应承诺的事情

- 未读取生产 NPC 价格、兑换规则的运营临时配置或实时玩家市场成交价；不能宣布整个现有游戏不存在套利。
- 2026-09-05 放开增金范围后，原白名单及 NPC 否决不再提供防套利保证。购买 / 转换 / 制作再点金的成本审计必须包含最多 10% 的额外基础收益与料理成本。当前回报比例最大 0.95 时，仅叠满料理的成功单次非幸运回报即可达到经济基准的 1.045 倍；失败率会降低期望，但不能以此断言所有循环无利可图。经济基准不是 NPC 售价。
- 快手加速全部合法点金材料。若原有购买 / 转换 / 点金循环已可盈利，它会提高处理速率；次数有限及消耗两尾鱼能限制规模，但不是数学上的无套利证明。
- 玩家主动低价出售材料产生的市场价差不是系统凭空造钱；本功能不保证抹平交易价差。
- 捕鱼 → 做料理 → 更好地捕鱼属于有材料、时间和失败成本的生产循环；需要控制净增效率，不应把所有正收益生产都定义成漏洞。
- 多助手共享时间能扩大鱼汤覆盖操作数，但每次仍真实消耗输入。时间型食品的单位资源收益需要用实际并发人数和库存统计验证。

## 实现与验收边界

点金与附魔各有独立规则处理器。前端数值计算在 `cuisine-operation-modifiers.ts`，点金资格请求封装在 `useTransmuteFood`；仍复用全局效果缓存与默认折叠的 `OperationEffectNotice`，控件旁使用 `FoodValueHint`。资格读取失败或缓存过期时不显示可用加成，服务端开工时再验证。

效果存在时，点金进入逐次实际开工 / 结算路径；不让一份快照复用到多个批量输入。无相关效果仍保留原精确 / 近似批量快进。原每块步数和执行时间预算未放宽。1 秒仅通过已冻结的点金加速快照豁免通用 2 秒底线；其他动作和无料理点金仍保留原底线。

附魔在原即时事务内校验装备、支付材料、扣料理次数与生成词条。事务失败一并回滚；预览不会消费次数。当前没有猫咪附魔入口，月璃只作用玩家，不伪造助手支持。

首轮验证包括：Go 规则 / 队列 / store / actionruntime / HTTP 回归、构建器不安全配置拒绝、前端数值 / 缓存 / 组件测试，以及本地 PostgreSQL 临时表内的共享次数、到期快照和扣次回执。首轮曾验证的 NPC 售价否决已随范围放开移除，由全部目录物品的准入一致性回归替代。此前浏览器检查使用真实 Vue 组件与隔离夹具，桌面及 390px 手机无横向溢出，默认折叠、耗时和概率提示可见，四个独立图标正常加载；该记录不是本次扩大范围后的浏览器复验。

这不是生产账号的完整制作 → 上架 → 食用 → 离线 → 附魔验收，也不是大并发压测。上述剩余验证需在部署前的测试账号完成。

## 发布与回退

- 本批四道料理不新增数据库结构，依赖已存在的全局效果表；已有迁移仍须按项目手动发布边界执行。
- 服务端、action-worker、前端及生成数据应作为兼容版本发布。旧服务端不认识新处理器，不能只部署新数据或前端。
- 不改写历史成品或已开工快照。出现问题时优先关闭新料理生产入口，保留读取新成品和结算既有快照的处理器；不要删除效果定义或清空玩家次数作为回退方式。
- 重点观察新增金币审计字段 `foodBonusGold`、每份消费次数、鱼汤有效使用次数及离线块耗时。没有本轮真实生产数据，不给出“零风险”结论。
