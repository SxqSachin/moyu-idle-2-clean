# 家具统一缓存与延迟生效

2026-09-06 实现记录。本文覆盖此前家具文档中的“每次运行读取家具来源”和“立即生效”描述。玩法、材料、等级和 DSL 原语不变。

## 运行时边界

- `furniture_effect_cache.go` 统一缓存每玩家的不可变、已解析来源区间。战斗、生活动作、钓鱼、实训台均复用该入口，不按家具 ID 分支。
- 固定租约 30 秒，从冷加载开始计时，命中不续租。无家具也缓存空结果。历史覆盖不足、过期、主动失效会重读，不能把不完整历史当作空效果。
- 同进程并发冷加载按玩家合并，房间内缺失玩家一次批量查询。已有房间成员列表直接传入，不重复查成员。
- LRU 最多 10000 玩家、估算 32 MiB；单玩家超过估算 8 MiB 不驻留。每玩家最多读取 4097 行，第 4097 行触发原有恢复预算错误。内存预算是估算值，不等于进程 RSS 上限。
- 热命中没有家具来源 SQL、Redis/NATS 请求或来源锁。冷加载是一次共享 advisory 锁语句和一次批量 SELECT；沿用 `(user_id, valid_until, valid_from)` 索引和历史清理上限。
- 缓存属于 Store/进程，重启自然失效。DSL 目录按既有启动加载方式部署；若将来支持原地热更新，必须统一清空来源缓存，不能直接修改已缓存的 rule/selector 切片。

## 生效协议

安置、升级、启用、暂停、补充在成功扣料后等待 60 秒生效。每件家具只允许一个待生效变更；其他家具不因此禁用。服务仍按时间消耗，无自动续费。

实例持久化目标状态、`effective_at` 和 `previous_state`。生效前 UI 显示原状态与倒计时；到点按时间投影切换，不增加定时任务或“升级完成”数据库写入。API 返回生效延迟，前端不硬编码策略数值。

暂停到点前维持旧效果并继续计时，到点保留当时的余量。升级报价以预计生效时的余量算维护补差，实际扣除不超过已确认报价。补给遇到旧服务先耗尽时允许出现服务间隙，不追补间隙收益。

来源区间仍为 `[from, until)`。旧尾部在生效点关闭，新来源从同一点开始；旧自然到期早于该点时不会被延长。动作、每竿和战斗 run 依旧在开始时冻结，当前进行中的工作不因升级而重新计算。离线快进使用历史开始时间匹配同一组区间，保留原预算、检查点与分片精度。

所有发布进程复用原 NATS 连接订阅 `runtime.furniture.changed` 广播。提交后本机立即失效，广播只加快其他进程刷新；丢失、乱序、重复通知最多引起延迟刷新或多读，不用消息里的状态覆盖数据库。租约 30 秒小于激活等待 60 秒，通知不是正确性的唯一依赖。

冷读和变更使用独立的 `cattery-source:<userId>` 共享/独占事务锁。变更在用户锁和全部库存扣除之后，修改来源之前取得独占锁；冷读先等共享锁，再用另一条 READ COMMITTED SELECT 读取提交后的来源。不能把锁和 SELECT 合为一条语句，也不能把这条冷读路径换成 Repeatable Read。战斗入场的库存锁早于来源锁，冻结后不再获取用户/库存锁；生活动作已先持有本玩家用户锁，后续沿用原账本流程。来源写事务取得独占锁后不能再获取新的库存锁。

API、action worker、battle worker 需要统一版本和正常时钟同步。现有游戏以服务端时间驱动动作，跨主机严重时钟偏移不在缓存容错范围；部署时监控时钟，30 秒差额不是可用的时钟漂移额度。维护命令有 5 秒上下文超时。

## 账务不缓存

库存、扣料回执、经验余数、累计贡献和已发奖励不进入本地来源缓存。生活动作仅在需要经验分享/在途分享时，每事务读取一次余数；不是每次循环读取。可变状态仍由原用户事务锁保护。

贡献按事务积累增量，以 `cattery_merge_contributions` 在一次 UPDATE 中合并，并同步提交经验余数。战斗不再先 SELECT 累计贡献再全量覆盖；返回总量仍在事务内校验，溢出或无效数据回滚。没有易丢失的内存奖励缓冲，也没有新发奖任务。离线报告的查看/确认语义不变。

这不等于整个战斗/动作结算零 SQL：原有结算持久化、账本和经验精度写入必须保留。优化目标是消除反复读家具规则和多余账务往返，而不是把权威库存和奖励换成最终一致的缓存。

## 前端读取

`GET /api/cattery/furniture?view=summary` 只读可用性、revision 和实例，不读库存、贡献统计，不生成报价；使用只读一致性快照，不抢用户事务锁。卡片和动作预览共享账号隔离的 30 秒前端缓存，合并正在进行的请求。

打开详情、刷新报价和手动刷新获取新数据。详情加载期间禁用操作；倒计时结束本地切换并补一次刷新。来源更新仍通过既有 WebSocket 推送，旧响应不得覆盖新 revision。网络结果不明确时保留同一个 requestId 和原报价重试，不生成新扣料命令。

## 性能证据

Apple M4 Pro 本机微基准，不代表生产吞吐：

| 范围 | 结果 |
| --- | --- |
| 4 玩家来源缓存热读 | 205.4 ns/op，424 B/op，5 次分配；SQL 计数保持初次加载的 1 次 |
| 原寻宝随机流构造 | 7949 ns/op，5603 B/op，8 次分配 |
| 复用随机对象与相同种子编码 | 7429 ns/op，0 B/op，0 次分配 |

随机流仍使用同一 SHA256 键和 Go 随机序列，不改变参战概率、普通战利品、奖励归属、重试结果或战斗主随机数。普通掉落 ID 排序移至敌人目录首次构建，不逐猫逐怪重复排序。

## 验证与发布

已验证来源正/负缓存、100 次战斗开始仅冷查一次、并发加载合并、取消等待、过期失败不回退旧规则、历史覆盖、LRU 上限、广播玩家隔离和独立随机序列。PostgreSQL 临时表/隔离 schema 验证了冷读等待提交、通知丢失、永久家具生效和升级、暂停计时、升级报价、扣料幂等、回滚和贡献报告。实际通用执行器、实训台在线/离线分片测试已切换到生产缓存策略。

前端 23 项定向测试、类型检查和 Vite 生产构建通过；构建仍有既有 geetest directive 与大分块警告，未运行额外压缩脚本。桌面 1280px、移动 320/360px 浏览器验证无横向溢出，图片已加载，待生效提交只扣一次，到点仅补一次刷新。浏览器使用真实 Vue 组件和隔离 API fixture，不是真实账号端到端或手机真机压测。全量 Go 回归尚有家具范围外的专精版本断言和炼金容量断言失败，未改动这些模块来绕过测试。

完成三轮检查：功能检查修复了前端待暂停状态到点后误保留旧到期时间；集成检查调整了来源写锁与战斗入场库存锁的顺序，并验证缓存下在线/离线分片一致；运行安全检查补上了失败回源向等待者传播错误，避免数据库故障时等待请求逐个重复回源。缓存与随机路径已通过竞态检测。

发布前先备份并暂停旧 API/action/battle 进程及写入口。按原顺序完成三个 `20260906_cattery_furniture*.sql` 迁移，再执行 `server/schema/migrations/20260907_cattery_furniture_cache.sql`，最后统一启动新服务并发布前端。已有库不执行 init.sql。此次没有迁移真实玩家表。

不要混跑旧 worker；旧代码不会理解待生效状态。出现问题先停写和相关 worker，保留期间历史、回执、奖励快照和新列，用兼容协议的修复版本恢复。不能直接删列或直接回滚旧二进制。生产多进程压力、真实账号断线重启路径和 DB CPU 变化仍需上线前验收；微基准不是这些验收的替代。
