# 猫舍家具系统设计草案

状态：历史设计草案。2026-09-06 用户已授权实现；实际契约与发布步骤见 [实现说明](cattery-furniture-implementation.md)。下文保留设计阶段措辞与示意 DSL，不代表当前实现状态。

最新需求：设计两件家具，书桌提供 15% 干活经验给玩家，第二件家具让参战猫咪概率参与战利品获取。第二件的详细玩法及战斗接入约束见 [战利品柜设计](cattery-furniture-battle-loot.md)。书桌原草案的 30% 已被 15% 替代；概率、维护数值和具体材料数量仍为建议，未获实现授权。

本轮只新增设计文档，不修改结算、库存、数据库或前端。文中的字段、模块、接口和数值均为拟议契约，不代表现有能力。

设计审查状态：已进行现场代码核对和三轮设计补充，尚未通过实现、真实数据库、在线/离线等价性或性能验证。准确性、兼容性与性能是验收门槛，不是当前已经兑现的保证；不以“架构看起来完整”替代验证。

## 1. 目标与现场结论

- 家具是需要长期供养的猫舍设施，不是一次购买后永久免费的被动属性。
- 书桌：猫咪执行适用动作时，向玩家额外提供对应动作经验的 15%，不扣除猫咪原有收益。
- 战利品柜（暂名）：符合资格的参战猫咪概率取得一次额外普通敌人掉落判定，不减少玩家原奖励，不增加战斗经验。
- 家具管理与效果计算分离；新家具优先只加数据，新机制只扩展对应领域处理器，不能在业务里检查书桌 ID。

参考项目 `../deep-article`：

- `shared/data/allKittyFurniture.ts`：书桌 35% 对应行动经验，耐久 100，每小时损耗 3；维修消耗铅笔、纸和书。
- `childProcess/run-task-standalone/src/process/runKittyTask.ts`：书桌判断及 `0.35` 直接写进动作奖励过程。
- `childProcess/run-task-standalone/src/cron/updateKittyFurnitureDurability.ts`：扫描启用家具并周期扣耐久。

借鉴“安装、开关、损耗、补充”的玩法，不沿用按家具 ID 硬编码效果、全服扫描掉耐久的实现。

本项目现场：

- `web/src/components/game/panel/cattery/CatteryFurnitureSection.vue` 目前仅占位。
- `server/internal/store/action_executor.go` 普通动作的经验入账目标是玩家；猫咪执行时乘 `KittyStatusExpMultiplier`，不是先给猫咪登记同一份动作经验。
- `packages/game-config/source/shared-global-config.json` 当前 `kitty.statusExpMultiplier` 为 0。因此不能在这个乘完倍率的结果上再乘 15%，否则书桌永远提供 0。
- `action_executor_fishing.go` 的猫咪钓鱼经验则入账猫咪自身；不能把普通动作的归属方式套给钓鱼。
- `action_executor_enhance.go` 当前有独立的玩家强化经验结算；建造执行器当前返回空经验。两者不能通过全队列兜底乘倍率来处理。
- 工作区已有 `operationeffect`、`docs/backend/operation-effects.md` 及相关未提交改动。它们可作为设计基础，但这里不宣称已经发布或全面验证。

## 2. 首版玩法建议

### 2.1 书桌

| 项目 | 建议 |
| --- | --- |
| 安装数量 | 每名玩家最多 1 张，作用于自己的全部猫咪助手 |
| 安装方式 | 直接消耗配方材料，不先增加家具物品、交易和制造链 |
| 初始状态 | 安装附带一份满补给，默认暂停，由玩家开启 |
| 效果 | 适用猫咪动作额外为玩家提供 15% 对应经验 |
| 补给容量 | 100，界面可以称为维护度；不与装备耐久共用逻辑 |
| 消耗 | 启用时每现实小时消耗 3，离线同样流逝 |
| 计费范围 | 按一张家具计费，不按猫咪数量翻倍；没有猫咪工作也会消耗，玩家可暂停 |
| 补充 | 每份指定库存材料恢复 30，约支持 10 小时；满额约支持 33 小时 20 分钟 |
| 耗尽 | 仅停止书桌效果，不销毁家具、不停猫咪动作、不产生欠款 |
| 暂停 | 保留未消耗的补给；恢复后继续计时 |
| 升级、拆除、摆放 | 首版不做；避免拆装刷新初始补给以及无必要的空间系统 |

这是“支付维护材料购买一段服务时间”，不是按点击次数收费。按家具固定时间收费能保留原版体验，并避免采集速度或猫咪数量直接改变补给消耗。

代价也要明确：猫咪越多，每份维护材料的收益越高。先把这作为养猫成长收益；以后若希望按猫咪工作量计费，应新增计费策略和版本，不能悄悄改变现有计费含义。

首版材料推荐使用已经存在的木材 `wood`、亚麻纤维 `flax_fiber`，分别体现维护和记录耗材。先不为一张书桌扩展纸、笔、书三条产业链。具体安装与补充数量待经济核算，不把参考项目的消耗数量直接搬过来。

补充按完整份数交易，服务器计算可容纳份数供展示，但提交时必须精确满足玩家确认的份数与成本；不足时整笔拒绝，不静默减量、增加份数或扣材料后截断。选择份数后展示成本与增加的服务时间。空维护量补充三份为 90，不标成“补满”；需要支持精确补满时另定按量配方，首版不假装存在这一能力。

首版只做主动补充。它仍是持续资源消耗点：维护度持续减少，长期使用就必须持续消耗库存。默认自动续费不是必要条件，后续另做显式开关、库存保留线、消耗预算及离线扣费时序，不预先塞入首版。

### 2.2 15% 的经验口径

建议玩家文案：**猫咪助手完成适用动作时，你额外获得该动作 15% 的对应经验。**

基础量 `sourceExp` 定义为该次猫咪操作按自身规则计算出的可结算动作经验，取经验归属转换之前的值；包括确实作用于该动作的经验修正，不包括书桌等派生经验。它不是玩家自己做同一动作时、带玩家专属加成的假想经验。

```text
普通动作 sourceExp = 本次 StatusExpReward + 本次有效 ExtraAttrExp
玩家既有经验 = sourceExp × 原 KittyStatusExpMultiplier
书桌额外经验 = sourceExp × 0.15
玩家总经验 = 玩家既有经验 + 书桌额外经验
```

当前全局倍率为 0，书桌生效后玩家实际获得 15%；不修改全局倍率。将来全局倍率提高，两项按明确的独立奖励相加，不隐式覆盖。

例：当前伐木动作对应采集经验 2，书桌增加玩家采集经验 0.3。原动作产出和经验规则不变。

猫咪钓鱼则从该竿原本应授予猫咪的钓鱼经验计算 15%，猫咪仍保留原本全部经验；不从猫咪等级经验、亲密度或战斗技能经验取值。等级封顶导致未能实际累加的部分不反向改变动作经验基础量，此处强调的是“对应动作经验”，不是数据库写入差额。

首版建议覆盖普通动作和猫咪钓鱼两类。普通动作包括可由猫咪执行、产出经验的采集和生产；鱼料理制作、实例绑定制作不能因为食物效果的防复制限制被误排除。

强化当前已有单独的玩家经验收益，是否额外再加 15% 需单独确认，本草案暂不接入。炼金、建造、战斗、委托、随记、技能书使用不在书桌首版适用范围；界面明示范围，不能写“所有经验”。战利品柜接入战斗掉落不代表书桌也分享战斗经验。后续接入其他动作，先定义该域的经验源与接收者，再复用规则。

不再次应用玩家自身经验倍率，不让书桌奖励触发自身或其他经验分享，避免二次放大、递归发奖。多种分享效果使用显式叠加组；首版 `owner_action_exp_echo` 组取最大值，不加算多件同类家具。

经验以现有四位小数精度入账。15% 换算保留更细的整数余数，按玩家、属性及稳定分享组持久化，避免逐次结算和批量离线因舍入得到不同总量；暂停、续费和版本更新不清空余数。余数仅用于数值精度，不再次乘倍率。

## 3. DSL：内容可配置，机制有类型

新增权威表 `packages/game-data/source/json/cattery_furniture.json`，家具定义分成三部分：

1. 内容：ID、版本、本地化、图标、安装条件、安装数量上限。
2. 维护：容量、消耗策略、补充配方与恢复量。
3. 效果引用：引用已经注册并校验的效果规则，而非脚本字符串。

以下是拟议结构示意；材料数量只是展示字段，尚未经济定案：

```json
{
  "id": "study_desk",
  "rulesetVersion": "study-desk-v1",
  "maxInstalled": 1,
  "installCosts": { "wood": 80, "flax_fiber": 40 },
  "upkeep": {
    "kind": "enabled_elapsed_time",
    "capacity": 100,
    "unitsPerHour": 3,
    "refill": {
      "costs": { "wood": 20, "flax_fiber": 40 },
      "restoreUnits": 30
    }
  },
  "effects": [
    { "definitionId": "furniture.study_desk.action_exp_echo" },
    { "definitionId": "furniture.study_desk.fishing_exp_echo" }
  ]
}
```

普通动作规则语义示意：

```json
{
  "id": "furniture.study_desk.action_exp_echo",
  "rulesetVersion": "owner-exp-echo-v1",
  "domain": "life_action",
  "kind": "life_action.owner_exp_echo",
  "allowedTargets": ["all_kitties"],
  "params": {
    "rate": 0.15,
    "basis": "operation_source_exp",
    "recipient": "owner",
    "stackGroup": "owner_action_exp_echo",
    "stackMode": "max"
  }
}
```

钓鱼定义使用 `fishing_cast.owner_exp_echo`，与普通动作域复用同一个经验纯计算器。此处故意不是可直接导入现有 `operation_effects.json` 的完整记录：现有 `Definition` 还把规则与食用授权的 lifetime/stacking 放在一起，实施时需要做下面的窄边界拆分，不能用缺字段 JSON 冒充已支持。

现有倍率、目标、动作分类 selector、配方、维护速度都应通过 DSL 调整。同一处理器语义下调参无需改结算代码；全新机制仍需新增强类型处理器与测试。**DSL 不承诺任意脚本都能改变全游戏。**

构建与启动双校验：未知 kind、未知物品或动作引用、非法目标、未适配的经验域、非有限数值、越界比例、不可容纳的补充量、未知字段均拒绝。编译后复用索引与已解析的参数，不在每次动作里解析全部 JSON。

## 4. 架构边界

### 4.1 家具生命周期独立，操作效果计算复用

| 层 | 拟议位置 | 只负责 |
| --- | --- | --- |
| 权威内容 | game-data 家具表及效果定义 | 配方、损耗策略、目标、规则参数、版本 |
| 家具领域 | `server/internal/catteryfurniture` | 纯维护度计算、有效时间段、状态转移 |
| 家具存储 | `server/internal/store/cattery_furniture*.go` | 所有权、用户锁、库存 ledger、家具状态和幂等事务 |
| 共用效果内核 | `server/internal/operationeffect` | 类型注册、筛选、来源标识、冻结快照 |
| 经验处理器 | `operationeffect/experience` 及领域适配器 | 接收原经验与快照，返回带接收者、来源的经验增量 |
| 业务入账 | 普通动作、钓鱼现有事务 | 原奖励保持不变，提交明确的额外玩家经验 |
| 展示 | 家具服务、store/composable、现有家具页 | 消耗投影、操作、收益摘要，不自行裁决效果 |

允许动作执行器调用统一的经验处理器；不允许出现 `if furnitureID == "study_desk"`。家具模块不能直接写 `player_attributes`，效果纯计算器不能访问库存或数据库，HTTP 不能计算奖励。

### 4.2 如何接上已有 operationeffect

复用已经存在的 Operation、registry、selector、snapshot 与领域 resolver，不另建家具专用的万能事件总线，也不强行套战斗 Buff DSL。

现有食物授权和家具不是同一种生命周期：食物按时间或次数消费，家具还可以暂停、维护和耗尽。因此不把家具伪装为食物物品，也不周期性给每只猫“重新吃一次永久料理”。

实施时从现有 Definition 中提取共用的强类型规则描述，保留现有食物 JSON/API 的兼容映射。家具的有效时间段向同一匹配与冻结流程提供规则；食物仍由现有 Grant/Session 管理次数消费。只抽取被两者实际共用的部分，不重写食物激活、叠加和离线恢复体系。

快照增加可辨认的来源 `SourceRef`：食物授权或家具运行区间，以及规则 ID/版本。保留旧 GrantID 的解析与原随机种子路径，不用虚构 grant ID 来代表家具。新快照结构必须版本化，并能读取旧快照；没有家具来源的旧运行按无家具效果处理。

经验规则只要求 `source_exp` 能力。当前普通动作上下文对料理制作、实例绑定制作存在整操作排除，这是现有食物返料/复制产物规则的限制，不能直接继承给经验分享。应把这些禁用条件限定到对应规则能力，保持原食物禁用测试不变，并为书桌单独添加适用性测试。

未来猫抓板缩短动作耗时，在操作开始阶段返回耗时修正；额外产出在奖励阶段返回产物增量；休息心情恢复需要独立的休息时间段适配器。不能因为已有动作事件就把休息、战斗、市场都塞进同一个 `map[string]any` 回调。

## 5. 时间、离线与结算契约

### 5.1 不需要定时扣耐久

服务端用整数时间和定点维护量，保存计时锚点与已经付费的有效区间，按实际经过时间推导余量。不要每小时遍历所有玩家 UPDATE，也不要靠客户端发耗尽请求。

启用时生成 `[validFrom, validUntil)` 运行区间，终点由当前剩余维护量计算。暂停关闭该区间并保存剩余量；恢复创建新区间。耗尽是时间事实，不依赖后台任务及时写入状态。

运行区间是启用期间计时与规则的权威；暂停余量只是关闭区间时的结转。界面倒计时是投影，不能另有一个会独立变化的“效果剩余时间”。维护速率、规则版本变化不能回头重算已经购买的区间。

### 5.2 每次实际操作开始时冻结

- 按一次普通动作或一次钓鱼抛竿判断，不按整条队列或整趟钓鱼只判断一次。
- 开始时间落在有效区间内，冻结本次书桌规则；结算时只使用快照，不读“书桌现在开着吗”。
- 耗尽、暂停发生前已经开始的操作仍享有本次收益；之后开始的操作不享有。恰好等于结束时间不生效。
- 中途启用、修复、安装均不补发当前已经开始的操作；取消且未产生原动作经验，不发书桌经验。
- 多只猫共享同一时间窗口，但各自按自己的操作快照计算，维护消耗仍只算一次。

这是与已有操作效果基座一致的开始时授权语义；并非按每一秒工作量拆分经验。界面说明“开关对下一次开始的操作生效”，避免误解。

### 5.3 绝不追溯使用今天的新补给

需要区分“花费库存”与“改变未来开关”，不能机械地复用食物补次数的恢复拦截：

- 安装、补充会花费库存，必须在用户锁内检查相关历史待结算操作。需要恢复的账号先走既有恢复流程，未完成返回恢复待处理状态，不扣材料、不改家具。否则今天补充可能抢走尚未结算的历史动作原本应使用的库存。
- 暂停不花费库存，允许在用户锁内立即截断服务器当前时刻之后的服务区间，并保留过去。不能因为某条历史通道暂停、参战或尚未恢复，就让玩家无法停止未来维护消耗。
- 恢复启用只使用已经购买的剩余维护量，创建从服务器当前时刻开始的新区间，不回填历史；不因仅存在历史欠结算而拒绝。这不改变任何猫咪队列的暂停/参战状态。

不能把数天离线恢复塞进一次无限时长的家具事务。若历史通道不能自动恢复，应明确指出需先处理该通道，允许玩家依现有规则选择恢复或取消，不由家具接口擅自改动它。

任何新运行区间的开始时间不得早于服务器本次操作时间。已经到期的旧区间不能通过续费跨越中间的断供时间；耗尽后补充创建新区间。暂停和补充时保留历史区间直到全部可能引用它的运行与离线恢复水位过去。

连续启用期间补充只增加尚未到期区间的未来尾部，而且必须在历史恢复边界检查通过后进行。旧运行中快照不可修改。

暂停命令与恢复切片在同一个用户锁下串行化，命令时间在取得锁后确定；过去区间与已开始的操作快照保持不变。运行区间的未来尾部可以关闭，不能把暂停写成“从旧恢复水位开始关闭”。前一轮草案中“所有家具操作均等待恢复”的规则由本节替代。

### 5.4 在线与离线同一套计算

离线按逻辑开始时间匹配历史区间，不按登录时间判断家具状态。收益在同一纯计算器计算，原始经验与派生经验分开累计。

固定时间维护不竞争共享动作次数，也不逐次读取库存。候选家具区间在用户事务内一次加载；无家具账号保留原快速路径。普通动作可按区间边界切分批量处理，不能因为一张书桌让所有猫咪全面退化为逐动作数据库访问。

即使首版先沿用现有逐操作内存推进，也必须有恢复预算和每批查询数上限；是否支持边界分段优化要以当前快进路径实测为准，不把已有批量能力当成无需改造的保证。

### 5.5 离线接入必须按能力统一，不能按家具接线

补充设计约束：**每个效果来源类型接入一次，每个业务领域接入一次；新增使用已有规则的家具，不修改在线或离线调度代码。** 首件书桌不能以在每个执行器新增书桌分支的方式交付。

当前可复用的接入位置：

- `action_queue.go` 在用户事务和用户锁内加载一次 `EffectSession`，传给运行项，在事务末尾统一写回效果消费；家具来源应接在这里，而不是在 HTTP、worker、每只猫和每个动作里各加载一次。
- `operation_effects.go` 的加载器会考虑待恢复时间范围，并非只查登录时仍有效的授权。家具也必须加载与恢复窗口相交的历史区间；不能只查当前启用的家具。
- `action_operation_effects.go` 已处理普通动作的逐操作开始快照；钓鱼的真正边界是 `rate_operation_effects.go` 的 `freezeFishingCastEffects`，不是整个出钓队列项。
- `action_queue.go` 目前针对跨角色共享次数限制批量，`action_executor.go` 的相关效果路径也可能逐次推进。这是现有保守基础，不等于书桌接进去就自动获得高效的分段批量。

目标链路如下，图中只有家具来源适配器认识家具存储：

```text
一次恢复事务：用户锁 + 已有恢复窗口与预算
  -> 批量加载效果来源：食物授权 / 家具历史服务区间
  -> 一个 EffectSession：规则、有效区间、来源及可变消费状态
  -> 统一批次规划：效果时间边界 + 原业务边界 + 跨通道依赖
  -> 原领域执行器：开始冻结 -> 领域结算 -> 有类型的结果入账
  -> 同事务提交：队列进度、收益、精度余数、消费与恢复进度
```

### 5.6 批处理契约：能力描述，而不是 furniture switch

在注册的规则处理器及领域适配器中增加有类型的快进能力描述，具体接口名在实施时确定：

| 能力 | 含义 |
| --- | --- |
| 可合并性 | 是否存在与逐次计算等价的批量 resolver；不能仅凭“没有随机数”推断 |
| 时间边界 | 生效、到期或参数版本变化时，下一次操作需要重新匹配 |
| 操作边界 | 次数、概率、返料、状态变化是否要求逐操作计算 |
| 读写影响 | 读取哪些业务状态、写入谁的哪些状态，是否会影响后续开始或其他通道 |

这些是处理器代码经过测试后登记的保证，不允许内容作者在 DSL 写一个 `batchSafe: true` 就绕过正确性检查。未知规则不允许加载；已经注册但没有批量等价性证明的规则默认精确推进。

统一规划器合并所有实际命中规则和业务限制，取最保守的有效约束。书桌可以合并，不代表书桌与返料、共享次数食物同时存在时也能合并；不能让某个效果覆盖其他效果的限制。

维护区间适配器统一提供下一次相关变化时间。领域执行器仍负责判断自己能批量多少个操作；规划器不能仅凭队列项的结束时间自行计算钓鱼竿数、强化次数或制作数量。

示例能力归类，不是按家具 ID 的运行时分支：

| 规则 | 默认推进方式 |
| --- | --- |
| 对应动作经验按比例额外授予主人 | 满足读写依赖约束时，可按稳定区间聚合源经验并结转精度余数 |
| 动作耗时修正 | 每次开始冻结耗时；稳定区间由支持该能力的执行器批量，边界处重算 |
| 概率额外产出 | 默认每操作确定性计算，可在内存循环后汇总入账；不逐操作查询家具 |
| 返还材料后可能允许下一次启动 | 必须保留结算、返还、下一次成本校验的顺序 |
| 多猫共享使用次数 | 按全局逻辑时间竞争同一池，不能先把一只猫整夜跑完 |

概率规则沿用稳定操作身份及独立随机命名空间；随机结果不能随恢复分片大小或批量数量改变。未来引入批量概率算法，必须证明与原逐次序列等价，而不是换成另一次抽样。

### 5.7 书桌不能只检查耗尽边界，还要检查跨角色因果

书桌维护时间不竞争共享次数，但它会写入玩家经验。玩家属性进展可能影响后续动作时长、条件或其他行为，因此“没有共享次数”不等于“可以任意跨猫咪和玩家通道批量”。当前普通动作开始路径确实读取执行者属性来计算效率，应以这个实际读取边界检查影响。

例如，猫咪在 21:00 获得经验，书桌同步给予玩家经验；玩家 21:01 开始的新动作必须看到此前已提交的变化，而不能看到猫咪次日 02:00 才应获得的经验。反过来，也不能把所有书桌经验拖到离线结束后才发，让玩家后续动作一直使用过时属性。

经验规则登记“写 owner 的对应属性经验/进展”，业务开始适配器登记相关读依赖。首版可保守使用 owner 属性级依赖，不需要立即构建字段级通用依赖图；只有证明更窄边界安全后才优化。

存在受影响的其他通道时，统一规划器不得跨越其下一次相关状态读取边界；不能证明可合并就按逻辑事件交错推进。没有相关读取，且业务可以提供等价聚合时，才合并处理。同时间事件顺序必须明确且稳定，沿用现有队列顺序与 ID 等稳定键处理平局，不能依赖 map 遍历顺序。

这个约束属于“效果写入其他参与者状态”的共用能力，未来其他家具、料理或新来源复用；不在调度器里判断经验来自书桌。新增效果需要使已冻结的属性/配装投影失效时，也在对应强类型业务适配器处理，不让家具模块直接改缓存。

### 5.8 时间分段示例与恢复中断

假设玩家 20:00 离线，次日 08:00 恢复，书桌在 02:00 耗尽：

- 20:00 至 02:00 之前开始的适用操作有书桌效果；之后开始的操作没有。
- 01:59:50 已经开始、02:00 之后才完成的那次操作仍使用原快照，不拆半次操作，也不因区间切分丢失结算。
- 区间边界约束的是下一次开始的规则选择，不是把当前已开始的操作强制终止在边界。
- 08:00 的补充不能改写上述历史服务区间。
- 区间内没有其他依赖时可批量；有返料、其他效果或跨角色读取时，继续遵守更细的边界。

每次恢复切片开始按其实际待推进范围加载所需来源，而不是每个动作查询。历史很多时允许按恢复窗口分页并受预算约束；不承诺无限历史一次装入内存，也不引入“每件家具一个查询”。家具效果为空时走原无效果路径。

已有运行快照负责当前操作；历史区间负责之后尚未开始的逻辑操作。窗口下界不能直接等同于登录时间，也不能不经检查套用队列级结束时间到有内部抛竿等子操作的执行器。由领域提供最早未冻结的逻辑开始边界，无法确定时宁可保守扩大加载窗口，避免漏掉历史有效规则。

若恢复预算耗尽在 23:00，提交到该水位的队列、经验、精度余数和效果消费，并保留进行中的操作快照；下一片从已提交状态继续。不能在每一片都按“离线 12 小时”重复扣维护，也不能以 UI 上 08:00 的耗尽投影过滤掉 23:00 仍该生效的历史规则。已付费区间的现实时间投影和模拟恢复水位是不同概念。

同一事务内需要观察到的经验、等级和库存变化必须即时反映到后续业务读取；批量写回只用于可延迟的账本/汇总，不能为了减少 SQL 把影响下一次开始的状态延迟到错误时刻。首版不承诺所有业务零逐操作 SQL，但必须做到零逐操作家具查询，并对有依赖的精确路径测量恢复吞吐。

### 5.9 扩展门槛与验收补充

- 新增另一张使用已有经验规则的家具：只添加数据、本地化和图标，不改快进、worker、HTTP 或执行器。
- 新增一种从未支持的动作效果：增加类型化处理器、能力描述及领域测试；只有出现新的业务阶段或状态读写契约时，才扩展一次领域适配器。
- 新增休息恢复等业务领域：接入该领域自己的时间推进器一次，之后此领域内的家具继续只加数据。不强塞进动作队列来制造表面统一。
- 自动续费或按工作量消耗是新的计费策略，不是普通家具配置。它引入历史库存可用性或共享预算竞争，必须先补齐统一消费与顺序契约；未实现的策略在构建时拒绝，不通过配置假装可用。

新增验收：不同恢复切片大小结果一致；跨耗尽边界的尾操作不漏不重；猫咪经验影响玩家后续动作时在线与离线顺序一致；书桌与料理共享次数/返料同时存在不越过限制；更换同类家具定义不需要修改调度器。性能验收记录无家具、单书桌、多猫与多效果四组的家具查询数、恢复耗时和处理动作数，不能只测试最终经验数字。

## 6. 持久化、接口与安全

建议最少三类家具专用状态，具体命名在实施时对齐 store 习惯：

1. `player_cattery_furniture`：用户、家具定义、暂停余量、当前区间、规则版本、revision；唯一 `(user_id, furniture_id)`。
2. `player_cattery_furniture_periods`：已付费服务区间、开始/结束时间、冻结规则和维护参数、关闭原因；按用户与时间范围加载，只清理已越过恢复水位的历史。
3. `player_cattery_furniture_commands`：安装、启停、补充的幂等凭证与结果；用户 + request ID 唯一，相同 ID 不同参数拒绝，避免网络重试重复扣费。

经验换算余数由经验处理器的持久化适配器独立拥有，不塞进家具展示配置。第一版只支持一种分享组，仍须明确组键而非用书桌 ID 硬编码。

安装/补充的库存扣除、家具状态、运行区间、幂等凭证及 revision 在同一事务提交。复用用户级事务锁和库存 ledger；没有可用库存就整笔失败，不借用已装备、队列预留或他人库存。

书桌经验和原动作奖励、队列进度在同一结算事务入账；以既有操作身份去重，快进批次记录稳定的操作范围，不能因重试多发。收益与消耗审计保留规则版本和家具来源；不用每个经验小数额再创建一条无限增长的独立日志。

接口范围：查询、安装、启用/暂停、按份补充。写请求带 request ID 与 expected revision；服务端决定成本、时间、效果和目标。revision 冲突只刷新状态，不自动重放扣费请求。

前端遵循现有单 store/composable 模式，账号切换时清理，迟到响应按认证 epoch 与 revision 丢弃；复用已有 bootstrap/WS 同步结构，不建立第二套全局轮询。

数据库迁移保留独立 SQL，遵守人工部署边界，不增加服务启动自动执行迁移。

## 7. 界面与收益可见性

复用猫舍“家具”入口。首版展示书桌和战利品柜两条设施内容，分别显示图标、效果、明确适用范围、维护度、预计耗尽时间、每份材料与恢复量。两件家具独立启停、独立补充，不共用隐藏维护池；公共设施组件按有类型的效果摘要渲染，不按家具 ID 编写两套页面。

状态分别为未安装、启用中、已暂停、补给耗尽；启停用开关，补充用明确的消耗确认与份数输入。启用前明确提示“离线及猫咪空闲时也消耗；关闭可保留补给”。

不做首版家具自由摆放、复杂房间编辑器或装饰评分。不要让一张书桌占满整页营销式介绍。

动作/离线摘要明确区分“猫咪原收益”和“书桌提供给玩家的经验”；现有汇总按执行者归类，不能只把额外玩家经验塞进猫咪 AttrExp 字段。新增有来源和接收者的附加经验摘要，旧字段含义保持不变。玩家属性同步与升级提示也必须覆盖猫咪操作触发的玩家经验变化。

### 7.1 布局和视觉边界

保持猫舍现有标签页结构，不重做猫咪、随记等其他页面；家具标签内部采用无额外外框的设施列表，避免在猫舍既有容器里再套多层卡片。首版不显示只有一个选项的分类筛选器，家具增多后再用同一列表增加筛选。

复用项目现有 Element Plus、GameDialog、物品图标/QuickRefWithRequire 和主题 token。当前默认浅色角色参考：表面 `#ffffff`、辅助面 `#fafafa`、边线 `#d2d2d7`、正文 `#1d1d1f`、次要文字 `#6e6e73`、操作色 `#0066cc`；实现应使用对应变量，深色与皮肤跟随全局，不把这些参考值硬编码成新主题。

沿用已有字体，设施名 16px 中等/半粗，正文 14px，辅助数据 12px；数字可用等宽数字特性。字距为 0，不以视口宽度缩放字号，不新增大标题字体与字体下载。主体辨识度来自匹配现有游戏风格的书桌图标，而不是大面积背景装饰。

桌面一条设施分为图标与名称、效果/维护信息、操作三段；窄屏改为名称与开关一行、效果与维护一行、补充操作一行。图标尺寸固定，长名称可换行，按钮不挤压说明。新增独立框体如需圆角不超过 8px，但不修改既有父容器样式。

设计线框示意，仅表达信息顺序：

```text
书桌                                      启用 [开关]
对应动作经验 +15%                     全部猫咪助手
维护度 64 / 100                        可用 21小时20分
预计耗尽：明日 14:20                    每小时消耗 3
                                             [补充]
```

“可用时长”是已有补给可支持的服务时间，不是经验收益预测；状态为暂停时不显示一个仍在走的耗尽时间。倒计时不作为 aria-live 每秒播报，图标与按钮有可访问名称，不以颜色单独表达启用或耗尽。

### 7.2 安装、启停、补充的完整流程

| 流程 | 交互与结果 |
| --- | --- |
| 未建猫舍 | 显示安装前置条件及明确的建造入口；是否满足由服务端判断 |
| 未安装 | 显示书桌、效果、安装成本，点击安装进入确认，不因打开页面自动扣费 |
| 安装确认 | 展示每种材料“需要 / 可用”、附带维护量、安装后暂停状态；成功后仍不自动开启 |
| 启用 | 已安装且有维护量才可启用；首次展示真实计费条件供确认，后续切换不重复弹无必要对话框 |
| 暂停 | 无消费确认弹窗，立即提交；成功后显示暂停与剩余可用时长，不等待历史恢复完成 |
| 补充 | GameDialog 显示维护量、每份恢复量、材料、份数步进输入、总成本和补充后时长 |
| 暂停时补充 | 只补充，不偷偷启用；成功后主页面提供原启用开关 |
| 启用时补充 | 成功后继续运行，服务端返回新的耗尽时间 |
| 耗尽时补充 | 成功后进入暂停；需要明确启用才开始消耗，首版不做“补充并自动启用”隐藏合并动作 |
| 没有猫咪 | 不没收家具；保持玩家选择的开关与计费规则，启用确认中显示当前无猫咪，不伪造预计收益 |

首版耗尽会结束本次启用意图，不保留隐藏自动续开标记。状态不能只靠 `enabled: true` 加负余量推断，需明确命令意图和服务截止；状态机以第 10 节为准。

补充步进器默认一份，最大可选份数为可用库存与容量共同允许的上限；不增加带有不明确消费含义的“最大”快捷扣费按钮。材料缺口直接在材料行显示，物品支持点击查看，移动端不依赖 hover。确认按钮显示“补充 N 份”，旁边保留总成本；材料价格/配方版本变动必须重新确认。

### 7.3 异步、失败和恢复

- 每件家具同一时间最多一个前端写请求，提交期间冻结该设施的相关控件并显示 loading，但不是锁死整个猫舍页面。
- 不乐观扣库存，不乐观切换持久开关；服务端成功快照才改变权威状态。客户端可显示“正在暂停”，不能提前宣称“已停止消耗”。
- 网络超时或响应丢失为“结果待确认”，不是“肯定失败”。保留 request ID，查询命令结果或用同一 ID 恢复原结果；查询结果前不允许用新 ID 再扣一次。
- revision 冲突、材料不足、定义版本变化均保留玩家输入，刷新最新状态，让玩家重新确认；不能自动重放消费。只重查状态的请求可以去重或重试。
- 暂停请求结果未知时提供状态刷新，不撤销本地待确认标记后假装仍启用；只在结果确定后展示明确的启用/暂停态。
- 历史恢复中：查询与暂停可用；安装/补充显示恢复状态和原因，不无声排队一个未来扣费命令，也不要求玩家刷新整页。
- 首次加载用稳定尺寸骨架；刷新失败保留最近一次数据并标记未同步。断网时禁用写入，不把旧倒计时当作服务器确认。
- 恢复页面可见、重连或收到更高 revision 时刷新；普通秒级倒计时只用一个页面级时钟，不触发秒级网络请求。
- 家具定义状态、库存状态和玩家属性可能来自不同同步通道，各自按所属 revision 更新；不能拿家具 revision 覆盖全局库存新状态。提交完成时按现有规范统一触发相关状态同步。
- 请求绑定当前账号认证 epoch；切换账号后丢弃旧响应、清理待确认状态缓存，并确保重新登录原账号时仍能通过服务器查到幂等结果。

### 7.4 响应式与可访问性验收

至少验证 360/390px 手机、768px 平板、1440px 桌面及深浅主题；200% 文本缩放下不出现按钮文字覆盖或横向溢出。手机交互目标至少 44px，弹窗内容可滚动、确认区不遮住最后一项材料，输入聚焦时不被软键盘挡住。

开关支持键盘且有状态标签；份数输入可键盘编辑，非法输入按明确范围校验。对话框焦点进入、关闭回到触发按钮；错误信息可关联输入，缺货与耗尽除颜色外有文字状态。六种现有语言都用本地化键和占位符，不拼接百分比或日期句子。

家具页不增加每次动作完成的弹窗或 toast；在线细项走既有奖励摘要，离线一次汇总按属性展开。“本次离线书桌贡献”只来自服务端实际已完成结算，恢复未完成时明确为阶段结果。首版不另建今日/累计收益排行榜与跨时区日结统计。

## 8. 经济验证与验收

材料定价基于：每账号猫咪数量、实际动作速度、每小时 sourceExp、全天开启率、每种原料每小时实际净产出。维护成本应占玩家愿意支付的一部分生产能力，而非迫使玩家长时间只给书桌打工。

先用单猫、常见多猫、上限猫数三组核算“每天材料消耗 / 每天额外经验”，再定安装与补充数量。固定 15% 是最新已知需求，100 容量、3/小时和 30/份只是首轮建议，可以在数据层调优。战利品柜另按战斗频率、参战猫咪数和普通掉落期望价值核算成本，不能照抄书桌价格。

实现验收至少覆盖：

- 当前基础倍率 0 时普通动作仍能正确增加 15%；无家具路径与既有行为一致。
- 钓鱼猫咪保留原经验，主人只得派生经验；不重复乘玩家专属倍率，不分享战斗或委托经验。
- 料理制作、实例绑定制作可正确分享经验，但现有料理返料和复制产物限制不被放开。
- 单次、多次、离线不同分片的经验、余数及维护余量一致。
- 同时运行多只猫不重复计时扣费；全局耗尽时刻和时间边界正确。
- 开始后暂停/耗尽、完成前补充、断供再恢复、运行中取消均遵守快照语义。
- 新安装和新补给不能提升过去的离线收益；暂停中的历史待结算通道也要检查。
- 两个客户端同时补充、网络重试、材料不足、事务中途失败不多扣不多发。
- 旧运行 payload、旧食物授权、版本升级、游戏数据不兼容配置、账号切换均有回归。
- 真正的玩家属性、升级通知、离线摘要、移动端家具页一致，不能仅验证静态 UI。

## 9. 建议实施次序与待确认项

第一步确认两件家具的经验口径、战利品参与语义和时间消耗方式；第二步实现共用家具数据、生命周期与事务；第三步接普通动作和钓鱼经验处理器，以及独立的战斗奖励领域适配器；第四步接公共家具界面与各领域收益同步；第五步完成在线/离线、战斗编译/回放/结算、库存并发与旧料理能力的回归检查。此处仅记录未来实施顺序。

待用户确认的主要玩法选择：

- 按最新要求将书桌改为“对应动作经验的 15%”；额外提供而非扣走猫咪所得的语义继续作为推荐方案，普通动作不顺便新增猫咪自己的生活经验体系。
- 家具按启用现实时间消耗，空闲与离线也消耗，可以暂停；首版手动补充，不默认自动扣库存。
- 首版普通动作 + 猫咪钓鱼，强化既有经验规则单独讨论后再接；安装和补充具体材料数量需经济核算。
- 战利品柜的参与概率暂拟 20%，按每只符合资格的参战猫咪、每个获胜波次判定；采用额外普通掉落而非争抢既有奖励，详见独立设计文档，尚待确认。

以上确认前不启动代码实现。

## 10. 设计审查补充：正确性与兼容契约

### 10.1 状态与事务不变量

| 当前状态 / 命令 | 状态变化 | 库存影响 |
| --- | --- | --- |
| 未安装 / 安装 | 唯一创建，满维护量，暂停 | 扣确认的安装成本一次 |
| 暂停且有余量 / 启用 | 以当前时间创建有效区间 | 无 |
| 启用 / 暂停 | 截断未来区间，结转剩余量；为 0 时显示耗尽 | 无 |
| 启用 / 到期 | 自然转耗尽，无需扫描写入 | 无额外扣费，之前已支付 |
| 暂停 / 补充 | 增加余量，仍暂停 | 扣确认份数一次 |
| 启用未到期 / 补充 | 延长未来服务，继续启用 | 扣确认份数一次 |
| 耗尽 / 补充 | 增加余量，转暂停 | 扣确认份数一次 |

相同 request ID 的重试优先返回原结果；不同 request ID 的重复启停在相同目标状态下为无额外作用，不刷新服务时长。非法状态转换不扣费。安装记录唯一约束与用户锁共同阻止重复初始补给。

持久状态不允许库存、维护量为负，余量不能越容量，有效区间不能倒置或在同一实例内重叠；零长度区间不参与匹配。同一来源在同一操作最多命中一次，经验增量必须有明确接收者。最高值叠加组遇到相同强度，使用版本化的稳定优先级及来源键破平局，不能让随机遍历顺序改变审计归属。

命令时间使用服务端在用户锁内确定的一次时间值，并与已提交锚点维持单调；不信任客户端时间，不在一个命令的多条 SQL 之间重复取不同决策时刻。操作 key 使用已经持久化的身份，避免数据库时间精度与 Go 时间精度差异导致重试产生新身份。

补充提交携带家具 revision、定义/配方版本、精确份数及幂等 ID；服务端以自己的定义复算成本。版本或成本与玩家确认不一致整笔拒绝，不只依赖前端旧价格。定义不可从客户端上传或替换。

处理器按固定精度规范接受源经验与比例，校验上限和整数溢出；余数与经验入账同事务提交。重复请求不能重复结转余数；比例为 0 或没有源经验不发奖，负经验不进入分享。统计汇总不能替代实际奖励事务。

### 10.2 “在线与离线一致”的准确含义

相同初始状态、相同规则版本、相同操作身份、相同逻辑开始与结束时间、相同外部事件顺序，单次推进、批量推进、不同恢复切片必须得到相同状态、原奖励、额外经验和维护余量。

不承诺“现实经过同样小时数，在线与离线必然完成相同动作数”。当前在线延迟结算后下一次可能以实际启动时刻开始，而离线使用计划逻辑时间线；家具不能为了表面一致擅自改写这项既有语义。应分别验证各自实际开始时间符合相同的效果规则，以及输入时间线相同时结果严格等价。

效果的有意收益改变，例如书桌导致玩家升级以及随后合法的效率提升，不属于应被禁止的副作用；无家具、未适用动作、原随机序列、食物消费契约、原猫咪收益等非目标路径才必须保持不变。

### 10.3 规则版本、旧数据与发布

- 冻结源经验的规则边界、比例、叠加语义、维护速度等行为变化需提升版本，已购买且冻结的服务与正在运行操作继续按原版本。明确的新版本生效边界之后才能选用新参数，不能用当前 catalog 重新解释历史。
- 首版不支持把不同维护速度/效果强度的服务量隐式混为一个余额。存在不兼容旧版本余量时，继续使用旧服务、禁止向其追加新版本补给，并在 UI 展示原因；耗尽后下一份使用新版本。未来若需要转换，必须有明确的迁移与补偿规则。
- 旧 payload 没有家具快照视为无家具；新快照损坏或 kind 不可处理不能静默当作无效果发完原奖励。应失败并保留可重试状态，定位具体用户/操作，不修改或删除其队列伪造完成。
- 不改写食物既有 grant ID、随机种子、叠加、恢复和扣次数逻辑。家具来源与食物来源共享匹配能力，但各自保留消费生命周期。
- 人工执行向后兼容的增量迁移，先部署能读取新旧快照的服务端与所有相关 worker，确认版本能力一致，再开放新家具写入口；最后发布对应前端/数据。不能让旧 worker 接到无法结算的效果。
- 关闭新安装入口不等于删除历史授权。普通下线停止新交易但继续兑现已购买服务与已开始操作；紧急停用若需要中止未来服务，应另有可审计的暂停与余量保护方案，不能直接删定义。
- 启用新来源后，不能直接回滚到无法读取新快照的旧二进制。回退版本必须兼容已发放状态；否则先完成受控排空/转换并验证，不允许通过删表或清队列“回滚”。

### 10.4 数据与运营边界

首版无家具交易、转移、拆除退款、自动补给、离线追加欠款。猫咪离队或数量归零不退费、不销毁家具，也不把别人的动作纳入目标。猫舍安装前置条件由服务端验证；建筑失去资格的运行策略在实施前核对现有建筑生命周期，不能只做 UI 隐藏。

历史区间和命令凭证要有保留策略：只有所有相关恢复水位、运行快照和必要审计引用均已退出才归档。未退出的区间不能按“超过 30 天”直接删除；不为处理新家具引入全服定期扫描。查询按用户、窗口与稳定游标加载，必要的索引通过实际 SQL 和 EXPLAIN 验证。

对运行区间数量、页大小、活跃来源数量、规则数、恢复 CPU/执行步数设服务器上限，参数由压测定案。达到历史容量上限不能挡住暂停；可拒绝继续新增服务段并说明原因，不可以丢历史以腾空间。重复启停请求限流，暂停保持可操作，避免恶意制造无限区间。

## 11. 验证计划与性能门槛

### 11.1 先证明再优化

先建立不批量的逻辑事件参考执行器用于测试，再对照优化路径；它不是第二套生产奖励逻辑，必须调用同一领域纯计算器。随机生成动作时长、服务区间、猫咪数量、开关时点、恢复分片和崩溃点，以属性测试比较结果。

| 验证层 | 必须提供的证据 |
| --- | --- |
| 纯领域测试 | 区间边界、状态机、补充容量、精度余数、叠加、源经验映射 |
| 快进差分测试 | 单步/批量/不同切片严格等价；跨猫咪与玩家的状态读取顺序正确 |
| 组合回归 | 书桌与现有料理、返料、共享次数、钓鱼失败/中断、实例制作组合 |
| 真实 PostgreSQL | 同账号并发事务、幂等重试、死锁/事务中断、库存及经验部分失败回滚 |
| 旧行为回归 | 无家具、暂停/不匹配家具、旧 payload、旧食物和旧客户端字段语义不变 |
| 玩家路径 E2E | 安装、开启、离线、补充、暂停、刷新、重连、多端冲突、账号切换及真实收益 |
| 版本兼容 | 混合部署阻断、新旧快照读取、旧版本服务兑现与回退约束 |

强制故障注入点包含：扣库存后、写服务区间前后、经验入账后但队列进度提交前、提交成功但 HTTP 响应丢失、恢复切片提交前后。每一处均验证不会重复扣费、重复奖励或丢失剩余服务。

### 11.2 性能目标不是一句“优秀”

基准固定硬件、数据库数据量、账号规模、猫咪数量与恢复时长，比较基线和新设计的 p50/p95 耗时、CPU、内存峰值、SQL 数、锁等待与单位秒推进操作数；重复采样区分噪声。规模采用实际配置上限及最长允许离线窗口，而非只测单猫几分钟。

硬边界：没有逐操作/逐猫咪/逐家具的家具查询；没有全服维护扫描；没有单操作重复解析全部 DSL；没有每件家具一个计时器或网络轮询；预算耗尽必须能持久化继续。新增家具表的读次数按每恢复窗口所需分页计，不与完成动作数线性增长。

无家具基准暂定新增 p95 开销不超过 5%，最终阈值需结合噪声与现有 SLO 确认，不把此数字写成已经达标。固定时间书桌、无跨通道依赖时，新增效果处理开销应随规则/有效区间数量和必要业务批次数增长，而非强制生成 N 份操作快照；跨通道依赖或概率效果需要逐操作时，测量并受现有恢复预算约束，不为了吞吐跳过因果顺序。

若安全实现只能显著降低恢复吞吐，应先缩小首版适用范围或优化领域批处理，再讨论发布；不能把“以后优化”当作默认验收。未经实际压测，不承诺耗时毫秒数或百万操作吞吐。

### 11.3 发布前停止条件

存在任何在线/离线差分、重复扣费/发奖、历史追溯生效、旧料理回归、无法暂停、账号状态串用、无界恢复、关键移动端控件不可用的问题，都不进入发布。不能以 UI 看起来正常或少量单测通过替代真实事务与玩家路径证明。

首版应交付书桌与战利品柜两个具体玩法，而不是只交付抽象框架；统一来源接入、明确副作用范围、恢复一致性、战斗奖励兼容与库存事务不得降级为后续工作。战斗波次是独立操作域，不能为了两个家具共用而把战斗加入生活动作队列。
